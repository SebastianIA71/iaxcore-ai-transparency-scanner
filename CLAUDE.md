# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

IAXCORE AI Transparency Scanner — a web tool that scans a public URL for observable AI-transparency signals (EU AI Act Art. 50-adjacent) and produces a signed, verifiable report. The full product/engineering spec is `IAXCORE_AI_Transparency_Scanner_v0.5.1_CONSOLIDADO.md` (filename says v0.5.1, content is v0.5.2 — read the doc header, not the filename) — **read it before making product or architecture decisions**, especially §5 (module contracts), §6 (result vocabulary), §9 (security-bloqueante requirements), §10 (build phases and their gates), and §15 (data model). The spec is written for an agent to build from and explicitly names non-negotiable decisions in its §21 ("Decisiones que Claude Code no debe tomar solo").

The product cycle is **Scan → Fix → Rescan → Verify**, built in phases (Fase 0 → 7) each with an explicit exit gate defined in §10.

**It's deployed and working:** `https://iaxcore-ai-transparency-scanner.vercel.app` is a real, live site (Vercel Hobby plan, project `iaxcore-ai-transparency-scanner` under team `sebastians-projects-f9814e95`). Submitting a URL on `/` creates an `Evaluation` and redirects to `/scan/{id}`, which polls until the scan completes and renders the report. There is **no separate worker process running anywhere** — Vercel Hobby's cron minimum is once a day, useless for near-real-time scans, so `POST /api/scans` runs the whole pipeline (`runWorkerOnce` from `packages/pipeline`) *inside its own request*, in `next/server`'s `after()` so the client response isn't delayed. This needed a serverless-compatible browser: `packages/scanner`'s `launchSecureBrowser()` detects `VERCEL`/`AWS_LAMBDA_FUNCTION_NAME` and launches via `@sparticuz/chromium` + `playwright-core` instead of Playwright's ~300MB bundled Chromium, which doesn't fit in a Vercel function. Two real deploy-time failures had to be fixed to get here (both now resolved, see git history): `@sparticuz/chromium`'s `bin/` binary assets weren't copied into the function bundle (`serverExternalPackages` alone doesn't do this — needed `outputFileTracingIncludes` in `next.config.mjs` too), and a job stuck `queued` from before this pipeline existed was blocking new scans via the per-IP concurrency limit (had to be cleared by hand once). `apps/worker` (the persistent poll-loop process) still exists and calls the exact same `runWorkerOnce` — it's just not what's running in production right now.

Fase 0 (core contracts), Fase 1 (immutable platform: DB, queue, signing, rate-limited API), Fase 2 (secure browser/SSRF), Fase 3 (T1 detector), and Fase 5 (T2 detector) are wired together end-to-end and verified against the live Supabase database with real signing keys: claim → running → `runScan()` (real navigation, manifest) → `t1Detector.run()` + `t2Detector.run()` in parallel (real channel/AI-evidence/disclosure detection; real visible-AI-label detection) → `Finding` rows persisted via `createFindings` → signed `ReportArtifact` whose canonical JSON includes those findings → `completed`, with the signature independently re-verifiable from what's in Postgres (see `packages/pipeline/src/index.integration.test.ts`, which needs `DATABASE_POOLED_URL` + `SIGNING_KEY_ID`/`SIGNING_PRIVATE_KEY_B64`/`SIGNING_PUBLIC_KEY_B64` and is skipped without them). What's still missing before these phases' exit gates are formally satisfied: Fase 2's SSRF battery hasn't been run against real hostile fixtures (only local-server tests), Fase 3's provider-signature/phrase-pattern lists are a seed, not the curated, accuracy-measured catalog the gate calls for (§10-Fase 3: "precisión de `action_recommended` ≥95% en corpus etiquetado" — no labeled corpus exists yet), and Fase 5's label patterns are likewise a seed (§10-Fase 5's gate — "T2 nunca produce fail ni action_recommended solo por no detectar una etiqueta" — is enforced by construction: T2 findings never carry an `assessmentStatus` at all). `Evidence` (screenshots) is never captured for either detector — only `Finding` rows.

Fase 4 (Fix/Rescan)'s pure-logic pieces exist in `packages/core` — `generateAiDisclosureFix()` (accessible ES/EN notice + HTML snippet + placement instructions, WCAG AA contrast verified by `contrastRatio()`) and `compareT1Assessments()` — and its exit gate is proven directly: a fixture goes from `action_recommended` to `aligned` after the generated notice is applied (`packages/detectors/src/t1Detector.test.ts`, last test). What Fase 4 doesn't have is a product surface — no Rescan button/API route, nothing links two `Evaluation`s of the same URL together; today a "rescan" is just calling `POST /api/scans` again with the same URL, which already works because nothing prevents it, but isn't surfaced as a feature.

`apps/web`'s `/scan/[id]` doesn't just print the spec's compact three-line T1 report — a bare `pagesAnalyzed: 1/5` with no context reads as broken, not as the scanner correctly hitting a safety limit. The page also lists each selected page's status and (for excluded ones) a plain-language reason, a blocked-requests count, the consent-banner interaction, a one-sentence explanation of the T1 verdict, and T2's labels if any were found — all sourced from `COPY.<locale>.scan.*` (`packages/core/src/copy.ts`) so the forbidden-word sweep in `copy.test.ts` covers it automatically. Both `/` and `/scan/[id]` are ES-only (`COPY.es`) — no locale switcher yet, even though `COPY` is bilingual underneath. Everything in spec §14's page list beyond those two (`/r/{shareToken}`, `/method`, `/fix/ai-disclosure`, `/verify`, `/privacy`, `/bot`) still doesn't exist, and neither does the email gate, PDF rendering, telemetry, feedback capture, or the paid "expediente completo" unlock that Fase 7 also calls for. There's no Playwright test suite for `apps/web` — everything about it (including the production deploy itself) has been verified manually with headless Playwright driven ad hoc, not committed as tests.

## Commands

```bash
# Install (also runs `prisma generate` via packages/db's postinstall)
npm install

# Build everything / one workspace
npm run build
npm run build --workspace=@iaxcore/core

# Test everything / one workspace / one file
npm test
npm test --workspace=@iaxcore/db
npx vitest run src/t1.test.ts        # run from inside the package directory

# Typecheck a single package (no root-level "typecheck" script exists)
cd packages/core && npx tsc -p tsconfig.json --noEmit

# Web app dev server
npm run dev --workspace=@iaxcore/web

# Worker (long-running poll loop, not used in tests)
npm run start --workspace=@iaxcore/worker

# Prisma (must run from packages/db — prisma.config.ts loads ../../.env itself)
cd packages/db
npx prisma generate
npx prisma validate
```

**Integration tests require a real Postgres connection and are silently skipped otherwise.** Every `*.integration.test.ts` file starts with `describe.skipIf(!process.env.DATABASE_POOLED_URL)(...)` — set `DATABASE_POOLED_URL` (and for the worker/signing ones, `SIGNING_KEY_ID`/`SIGNING_PUBLIC_KEY_B64`/`SIGNING_PRIVATE_KEY_B64`) to actually run them, e.g.:

```bash
cd packages/db && DATABASE_POOLED_URL="postgresql://..." npx vitest run
```

Put the client construction (`createPooledClient()`) inside a `beforeAll`, not the `describe` body — `skipIf` skips hooks along with tests, but code that runs directly in the `describe` callback executes during test collection regardless of the skip.

## Architecture

**Monorepo, npm workspaces.** `apps/*` are deployables, `packages/*` are the shared engine:

- `packages/core` — pure logic, no I/O: the closed vocabulary (`ObservationStatus`, `AssessmentStatus`, etc. — `warning` must never appear in any of them, it's an explicit non-status), `deriveT1Assessment()` (the only function allowed to compute T1's assessment, per spec §5.1's derivation table), zod schemas for every entity in §15, Ed25519 signing (`signCanonicalJson`/`verifyCanonicalJsonSignature`) over a deterministic canonical JSON string (`canonicalizeForSigning` — sorted keys, no whitespace), `hashIp()`, copy dictionaries + forbidden-word checks, and the generic `Detector` contract that T1/T2/T3 implement. `fix.ts` (Fase 4) generates the accessible AI-disclosure notice (`generateAiDisclosureFix(locale)` — its ES/EN text lives in `COPY.<locale>.fix`, not a separate dictionary, specifically so `copy.test.ts`'s forbidden-word sweep covers it automatically) and exposes `contrastRatio()` (plain WCAG 2.1 §1.4.3 math — no dependency pulled in just for this) to verify the snippet's default colors meet AA. `rescan.ts`'s `compareT1Assessments(before, after)` is the only "Rescan" logic that exists — see below. The package's `index.ts` barrel pulls in `signing.ts`/`privacy.ts`, both of which use `node:crypto` — fine for server code, but webpack can't bundle that for a browser, so `package.json` also exports a `./copy` subpath (`"@iaxcore/core/copy"`, resolving straight to `copy.ts`, no `node:crypto` in its import graph) for client components to import `COPY` from instead of the barrel.
- `packages/db` — Prisma repository layer. Nothing here does its own business logic beyond enforcing the invariants below; `packages/core`'s zod schemas validate at the write boundary instead of relying on Postgres enums for everything (see "detectorId is a String" below). `findings.ts`'s `createFindings` writes several `Finding` rows from one detector run in a single `createManyAndReturn` (so their ids come back for `Evidence` to link to later); `findFindingsByEvaluation` orders by `id` ascending — Prisma's client-generated `cuid()`s are lexicographically creation-ordered, and `createdAt` is identical across a whole `createFindings` call so it can't be used to recover insertion order. There is no `Evidence` repository yet — nothing captures screenshots.
- `packages/detectors` — `t1Detector` implements `Detector<"t1">` for real: it opens its own SSRF-guarded page (via `@iaxcore/scanner`, independently of `runScan()` — `packages/core`'s `Detector` contract can't carry a `Page`, so each detector navigates on its own), finds and passively opens a chat/interaction widget (`channel.ts`), classifies AI-vs-human evidence and disclosure timing from the panel's visible text plus a seed provider-signature list (`signatures/index.ts`) and ES/EN/FR/DE/IT/PT phrase patterns (`patterns.ts`, `classification.ts`), and assembles the three §5.1 sub-findings plus the `t1.assessment` rollup via `deriveT1Assessment()`. `t2Detector` implements `Detector<"t2">`: same independent-navigation pattern, but only inspects the single `finalUrl` page (§5.2 explicitly postpones following linked pages) for visible AI-content labels — `figcaption` text, `alt`/`aria-label` on `img`/`video`/`audio`, and short (`labelDetection.ts` caps candidates at 200 chars) text inside a `<figure>`. It matches `AI_LABEL_PATTERNS` (`patterns.ts`) only against those DOM-position-filtered candidates, never against the page's general body text — that position+pattern combination, not the pattern list alone, is what keeps a false positive like F12 (an article whose prose happens to discuss "AI-generated content") from counting as a label. T2 findings never carry an `assessmentStatus` (§5.2's "regla dura": never `action_recommended` just for an absent label — enforced by construction, not by a check). Both detectors' signature/pattern lists are intentionally a seed, not a finished catalog — see the B1 comment in `signatures/index.ts`. `runT1Detection`/`runT2Detection(evaluationId, finalUrl, options)` are the testable inner functions (`options.resolveHostname` lets tests point them at a local server, same pattern as `runScan`); `t1Detector.run()`/`t2Detector.run()` are the thin `Detector`-shaped wrappers `packages/pipeline` calls. `finding.ts`'s `buildFinding()` is the shared `Finding`-object constructor both detectors use. `t3Detector` is still a typed stub throwing "not implemented" (T3 is never-in-this-pilot, §5.3).
- `packages/scanner` — the SSRF address classifier (`checkUrl`/`classifyAddress`), the browser wrapper with its request-interception SSRF guard (`installSsrfGuard`, byte/redirect/request limits), robots.txt parsing, deterministic page selection, consent-banner handling, a local `EvidenceStore`, and `runScan()` — the orchestrator that ties all of the above into one full scan and produces the per-evaluation manifest (`pages` with completed/excluded status and exclusion reason, `blocked_requests`, `consent_interaction`) that spec §10-Fase 2's exit gate requires. `launchSecureBrowser()` (`browser.ts`) is two implementations behind one function: locally (and in `apps/worker`) it's plain `playwright`; when `isServerlessRuntime()` sees `VERCEL` or `AWS_LAMBDA_FUNCTION_NAME` in the environment, it launches via `@sparticuz/chromium` + `playwright-core` instead, because Playwright's own bundled Chromium (~300MB) doesn't fit in a Vercel function. Only the environment-detection logic is unit-tested (`browser.serverless.test.ts`) — the actual serverless launch can only be verified deployed, since `@sparticuz/chromium`'s binary is Linux-only and won't run on a Windows/macOS dev machine.
- `packages/pipeline` — `runWorkerOnce(db, config)`: claim a job → mark running → `runScan()` the requested URL (`@iaxcore/scanner`) → `t1Detector.run()` and `t2Detector.run()` in parallel against the scan's `finalUrl` (`@iaxcore/detectors`) → persist their findings via `createFindings` → sign a canonical report that includes those findings → `completeEvaluation` with the scan's `finalUrl`/`pagesAnalyzed`/`manifest` → finish job. Extracted out of `apps/worker` into its own package because two different callers now need the exact same sequence: `apps/worker`'s persistent poll loop, and `apps/web`'s inline in-request trigger (see the top of this file for why the latter exists). Independently unit-tested with `@iaxcore/db`/`@iaxcore/scanner`/`@iaxcore/detectors` all mocked, and separately verified against live Postgres (`index.integration.test.ts`). The canonical report's `findings` array is built from the detectors' output mapped to `{detectorId, observationStatus, assessmentStatus, confidenceBand, summaryKey, detail}` — deliberately omitting `evaluationId` (redundant with the top-level one) and the DB-generated `id`/`createdAt`, so the signed payload is derivable from detector output alone, not a DB round-trip.
- `apps/web` — Next.js App Router, deployed to Vercel (see the top of this file). `app/api/scans/route.ts` (POST, rate-limited) creates the `Evaluation`+`ScanJob` and then, in `triggerInlineWorkerTick()`, calls `runWorkerOnce()` from `@iaxcore/pipeline` inside `after()` — this is the whole reason `apps/web` now depends on `@iaxcore/pipeline`/`@iaxcore/scanner`/`@iaxcore/detectors` (added to `transpilePackages` in `next.config.mjs`) and needs `SIGNING_KEY_ID`/`SIGNING_PRIVATE_KEY_B64` set in its own environment (previously only `apps/worker` needed them). `route.ts` also sets `export const maxDuration = 60` — Vercel's per-route opt-in, without it the function gets cut off well before a slow multi-page scan finishes. `app/api/scans/[id]/route.ts` (GET) returns `manifest`, `reportHash`, `signatureId`, and `findings` (the last only once `status` is `completed`/`failed`, fetched via `findFindingsByEvaluation`). `app/page.tsx` (`"use client"`) is the landing form — submits to `POST /api/scans`, redirects to `/scan/{id}` on success. `app/scan/[id]/page.tsx` (`"use client"`, reads the id via `useParams()` — not the `params` prop, that's the Server Component pattern) polls `GET /api/scans/{id}` every 2s while `queued`/`running` and, once `completed`, renders both the spec's compact three-line T1 report and the plain-language explanation described at the top of this file. `lib/db.ts` holds a per-process singleton `PrismaClient` — don't call `createPooledClient()` per-request, it exhausts the connection pool. `next.config.mjs` also carries `serverExternalPackages: ["playwright", "playwright-core", "@sparticuz/chromium"]` (keeps webpack from trying to bundle their native/binary internals) and `outputFileTracingIncludes` for `/api/scans` (forces Next to actually copy `@sparticuz/chromium`'s `bin/` assets into the deployed function — `serverExternalPackages` alone doesn't do this, and its absence is a silent runtime-only failure, not a build failure).
- `apps/worker` — `src/main.ts` is the persistent polling-loop process: `for (;;) runWorkerOnce(db, config)` from `@iaxcore/pipeline`, using `createDirectClient()` (needs `DATABASE_URL`, not the pooled one — see below). It's not what's running in production right now (see the top of this file) and isn't covered by tests; `apps/web`'s inline trigger and this loop call the identical `runWorkerOnce`, so nothing about the pipeline itself differs between them. `evaluation.pagesRequested` (fixed at creation, §9's "hasta cinco páginas" cap) is passed to `runScan()` as `maxPages` — a cap set before the scan runs, not something the scan itself decides.

### The Evaluation lifecycle (Fase 1's core invariant)

`Evaluation.status` only moves `queued → running → completed` (or `→ failed`), and each transition in `packages/db/src/evaluations.ts` is a **conditional `updateMany`** gated on the expected prior status (`where: { id, status: "queued" }`, etc.), not a plain `update`. Zero rows matched means someone already moved it — the functions throw `ImmutableEvaluationTransitionError` rather than silently no-op. This is the entire immutability mechanism; there's no DB trigger enforcing it.

### Rate limiting is defense-in-depth, not just an app-level check

§9 requires "cuota diaria + concurrencia máxima de 1 escaneo por IP" as a testable requirement. `packages/db/src/rateLimit.ts`'s `assertWithinRateLimit` does the count-based check (has a TOCTOU race by itself), but the real guarantee is a **Postgres partial unique index** — `evaluations_one_active_per_ip` on `(requesterIpHash) WHERE status IN ('queued','running')` — that can't be expressed in `schema.prisma`'s DSL (no partial-index syntax) and was applied as a hand-written migration instead (see "Schema changes" below). `createRateLimitedScan` catches the resulting `P2002` and re-throws it as the same `RateLimitExceededError`, and creates the `Evaluation` + its `ScanJob` in one `$transaction` — doing those as two separate calls was a real bug caught mid-development (a failed second insert would strand a `queued` evaluation the worker can never see, permanently occupying that IP's one concurrency slot).

### Queue: Postgres `SKIP LOCKED`, no Redis

`packages/db/src/queue.ts`'s `claimNextScanJob` is a single raw-SQL `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING ...` — one round trip, which is why it works fine over a pgbouncer transaction-mode pooled connection (see below) even though Prisma's own CLI commands don't.

### Detector IDs and a couple of other fields are plain strings, not Postgres enums

`Finding.detectorId` (`"t1.channel"`, `"t1.ai_evidence"`, etc.) and `ReportArtifact.format` are `String` columns in `schema.prisma`, validated by `packages/core`'s zod schemas at the write boundary — Prisma enum values can't contain dots, so the spec's dot-separated detector IDs can't be native Postgres enums. `ObservationStatus`/`AssessmentStatus`/`EvidenceConfidenceBand`/`EvaluationStatus` *are* native enums, matching `packages/core`'s vocabulary constants exactly.

## Environment-specific things that will bite you

- **Prisma 7 moved connection config out of `schema.prisma`.** `datasource.url`/`directUrl` in the schema file now error at parse time. The CLI (`migrate`, `validate`, `generate`) gets its connection from `packages/db/prisma.config.ts` (which loads the repo-root `.env`); the generated `PrismaClient` gets its connection at runtime via a **driver adapter** (`@prisma/adapter-pg`'s `PrismaPg`), constructed in `packages/db/src/client.ts`'s `createPooledClient()`/`createDirectClient()` — not read from env automatically.
- **`DATABASE_URL` (direct, port 5432) may be unreachable** in sandboxed dev environments — Supabase's direct connection is IPv6-only by default, and some environments have no IPv6 route (`nslookup` will show only an AAAA record, no A record). `DATABASE_POOLED_URL` (Supavisor, port 6543) is the fallback that actually works; single-statement raw SQL (like the `SKIP LOCKED` claim) is fine over it, but Prisma's own migrate/status/resolve commands hang indefinitely over it because they hold advisory locks across multiple round trips, which pgbouncer transaction mode can't sustain.
- **Schema changes that need the Prisma CLI to actually run against the live DB won't work from an environment without direct-connection access.** The workaround used throughout this project: generate the SQL by hand (or via `prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script` for a from-scratch schema), apply it directly through Supabase's MCP `apply_migration`/`execute_sql` tools (HTTPS management API, bypasses the Postgres wire protocol entirely), then manually record it in `_prisma_migrations` (`id` = a fresh UUID, `checksum` = the sha256 hex of the migration file) so a future `prisma migrate deploy` from an environment that *does* have direct access won't try to reapply it. `prisma migrate dev` only diffs against `schema.prisma`, so a construct that's applied via raw SQL but documented only in a schema comment (like the partial unique index above) survives future migrations undisturbed.
- **Next.js can't resolve this monorepo's workspace packages without help.** `packages/core`/`packages/db` use NodeNext-style imports (`import "./foo.js"` pointing at `foo.ts`) — `tsc` and `vitest` resolve this natively, Next's webpack doesn't, even with `transpilePackages` set. `apps/web/next.config.mjs` sets `webpack: (config) => { config.resolve.extensionAlias = { ".js": [".ts", ".tsx", ".js"] }; return config; }` to fix it. Any new Next app added to this repo that imports a workspace package will need the same fix.
- **RLS is off by default on every new Supabase table** and Supabase's advisors will flag it as critical (the `anon` key is public — it ends up in the browser bundle via `NEXT_PUBLIC_SUPABASE_ANON_KEY`). This project only ever accesses Postgres via Prisma using the `postgres` role, which bypasses RLS, so the fix applied has been "enable RLS with zero policies" on every table — that blocks all `anon`/`authenticated` access without affecting Prisma. If anything ever needs the Supabase JS client / anon key for real data access, RLS policies need to be written first, or it'll get zero rows back.
- Root `.env` (gitignored) holds real credentials for the live Supabase project, not a local-only database — there's a `docker-compose.yml` for a local Postgres alternative, but it's unverified (no Docker in some dev sandboxes).
